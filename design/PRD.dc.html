PR Stack Monitor — Product Requirements Draft v0.1 · August 2026

PR Stack Monitor

A macOS menu bar app that answers one question at a glance: is anything waiting on me, and did my merged work reach production?

Status: draft for review · Owner: engineering tools · Companion design: Tray App (option 2a)

1. Problem

An engineer working across several Linear projects routinely keeps ten to twenty pull requests open at once, many of them arranged in stacks where each PR is based on the one below it. GitHub's own surfaces answer "what PRs exist"; they do not answer "which of these is blocked on me right now", "which stack is stuck and at which layer", or "has the squash commit for this merged PR actually shipped to production yet".

Today that state is reconstructed manually — several browser tabs, the Linear board, and a CI/deploy dashboard — several times a day. The cost is not the time spent looking; it is the reviews and failed deploys that go unnoticed for hours because nobody was looking.

The app is an observer. It does not attempt to replace GitHub or Linear for doing work; it replaces the act of checking.

2. Goals and non-goals

GoalsNon-goals
Surface, without interaction, whether anything needs the user's attention — via the menu bar icon alone. Reviewing PRs, approving, commenting, or merging from inside the app.
Show every non-draft PR authored by the user, grouped by Linear project, in one scroll with no tabs or filters. Tracking PRs where the user is only a reviewer.
Make stack structure and the position of a blockage inside a stack legible at a glance. Creating, restacking, or rebasing stacks.
Follow a merged PR's squash commit through staging to production and say when it is live. Triggering, retrying, or rolling back deploys.
Let the user clear finished work out of the list so the panel stays short. Historical reporting, cycle-time analytics, or team dashboards.

Drafts are excluded by definition: the app covers PRs from the moment they enter review.

3. Information model

EntityDefinition and source
Pull requestA non-draft, open or recently-merged PR authored by the user, from GitHub. Carries title, number, age, review state, check state, mergeability.
ProjectThe Linear project of the issue the PR is linked to (via branch name or PR title/body reference). PRs with no linked issue, or an issue with no project, fall into Other.
StackA chain of the user's own open PRs where each PR's base branch is another PR's head branch. Derived entirely from base/head relationships — no tooling-specific metadata required. The base of the stack targets the trunk; the top is the most recent descendant.
ReleaseA git tag that contains a merged PR's squash commit. A PR is considered shipped when a tag containing its merge commit has completed its production deployment.
Deploy stageThree ordered stages: preview (checks on the PR branch), staging (merged to trunk and deployed to staging), production (tag containing the merge commit deployed to production).

4. Menu bar icon

The icon is the product's only always-visible surface, so it carries exactly one signal at a time, in a strict priority order. Higher rows win.

StateAppearanceTrigger
Action neededRed badge with a countChanges requested on the user's PR, CI failure, or merge conflict. The count is the number of such PRs.
Deploy in flightAmber dot, slow pulseA tag containing one of the user's merge commits is mid-deployment. Resolves to unread when it reaches production, or to action needed if it fails.
Unread activityIndigo dotNew comments, a new approval, or a PR becoming mergeable since the panel was last opened.
IdlePlain glyphNothing new since last read.
DisconnectedDashed glyph, dimmedNo credentials, expired token, or offline. Never silently shows stale data as if fresh.

Opening the panel clears unread but never clears action needed — a failing check stays badged until the underlying condition resolves or the PR is snoozed. The badge is monochrome-safe: shape and position, not colour alone, distinguish the states, so it survives dark menu bars and reduced-colour accessibility settings.

5. The panel

A single popover, roughly 440 points wide and up to 800 tall, anchored under the icon. One scrolling list, no tabs, no segmented control, no filter bar. Everything the user tracks is on one screen; the only structure is project headings.

5.1 Order

Sections appear in a stable order — Linear projects by most recent activity, then Other, then Done. Within a project, stacks come before loose PRs, and stacks are drawn top-most PR first, base last, matching how the branches sit on top of each other.

Rows are deliberately not re-sorted by urgency. Position stability is what makes the panel scannable day to day; urgency is carried by the appearance of the row, not by its place in the list. There is no summary banner counting problems — if the rows cannot communicate it, the row design is wrong.

5.2 Row anatomy

ElementBehaviour
Unread dotLeading indigo dot when the PR changed since the panel was last opened. Absent otherwise; the gutter is reserved so rows never shift.
Status iconA single tinted chip carrying the PR's overall state: in review, approved, blocked by a parent, changes requested, checks failing, conflicted, merged, closed. A row that needs attention always has a matching icon — a green icon never appears in a tinted row.
Stack spineA hairline connecting the status icons of consecutive members of a stack. No box, no indentation: stacked and unstacked PRs share one left edge, so the list keeps a single rhythm.
TitlePR title, single line, truncated with an ellipsis. Weight increases slightly when the row needs attention.
Meta lineLinear issue identifier, PR number, the one most important status phrase, and age or time since last activity. The status phrase is the only coloured token.
ReviewersUp to three avatars, overlapping by 2 points, each ringed in the colour of that reviewer's state: approved, changes requested, or pending. A count replaces the overflow.
Deploy trackThree short segments for preview, staging, production. The first segment carries CI state — green passing, red failing, amber running, grey none — so there is no separate CI icon to confuse with review state. Later segments fill as the change advances; the active one pulses.

Rows needing attention are marked by a warm background tint alone — no accent rule, no icon pile-up. Merged and closed rows use a muted title.

5.3 Done section

Merged PRs that reached production, and PRs closed without merging, collect in a trailing Done section. Each row can be dismissed individually, and the section header offers Clear all. Dismissal is local and permanent for that PR — it never re-appears, even if a later event touches it. A merged PR whose deploy is still in flight stays in its project section until it lands, because it is still information the user is waiting on.

6. Stacks

A stack is rendered as a run of adjacent rows joined by the spine. Members are ordered top-most first; the bottom row is the PR based on the trunk. A PR whose parent is not yet merged shows waiting on #NNNN in its meta line and a neutral status icon: it is not the user's problem until the layer beneath it clears.

When the number of open PRs makes full expansion impractical, a stack may collapse to a single summary row: name, member count, one segment per member coloured by that member's state, and the position of the first blockage. This is a scaling affordance, not the default presentation.

7. Deployment tracking

On merge, the app records the PR's squash commit. It then watches the repository's tags; when a tag contains that commit, the PR is bound to that release and follows the release's deployment status. Because a release usually carries several of the user's PRs, they advance together.

Three outcomes matter. Reached production is a notable event: it sets the unread dot, and the row moves to Done on next open. Deploy failed or held raises the row to action-needed and badges the icon. Not yet tagged is quiet — merged to staging, waiting for a release cut, with the third segment empty.

Merge commits are matched by the commit recorded at merge time, with a fallback to matching the PR reference in the commit message, so squash-merges with rewritten history still resolve.

8. Interactions

ActionResult
Click a rowOpens the PR on GitHub in the default browser and marks it read.

SnoozeSuppresses a PR's attention state until a chosen time. Snoozed rows render dimmed with the wake time in the meta line.

RefreshForces an immediate sync; the footer reports the time of the last successful one.

9. Data and sync

GitHub supplies pull requests, review state, checks, mergeability, merge commits, tags and deployment status. Linear supplies the issue-to-project mapping. Both are read-only scopes.

Polling is adaptive: frequent while a deploy is in flight or the panel is open, slower when idle, suspended on sleep and on battery below a threshold. The footer always states how fresh the data is, and stale data is visibly marked rather than silently shown. An expired token replaces the header with a reconnect banner over the last known list.

10. Edge cases

  • A PR is linked to no Linear issue, or to an issue with no project — it lands in Other.
  • A PR moves out of draft — it appears; a PR converted back to draft disappears without a notification.
  • A stack member is merged out of order — the spine reflows and the remaining members re-target; no error state.
  • A release is never cut for a merged PR — it sits at staging indefinitely and is not surfaced as a problem.
  • A production deploy is rolled back after being reported live — the row returns from Done with an action-needed state.
  • Nothing to show at all — the panel states plainly that everything is clear rather than rendering an empty list.

11. Visual direction

Native macOS structure — popover geometry, control sizing, system typeface, no custom chrome — with GitHub's semantic state colours and Linear's typographic restraint and spacing. Light appearance is the reference; the same palette maps to dark.

Specifics established in design: no monospaced type anywhere, numerals set with tabular figures instead. No decorative colour — project headings are plain text, never coloured bullets, so colour means status and nothing else. Rows sit on a lightly grey panel field, with state carried by tint. Reviewer avatars use a thin light ring separated by a one-point halo in the row's own tint.

The full state set is documented in the companion design file: needs-attention, all-clear, deploy in flight, heavy load with collapsed stacks, and first-run/disconnected.

12. Open questions

  1. Should reaching production raise a system notification, or only the menu bar dot?
  2. Is a keyboard-driven open-and-jump worth building, or is the panel purely pointer-driven?
  3. How many repositories does a single user realistically span, and does the row need a repository name once that number exceeds one?
  4. At what open-PR count should stacks collapse automatically?
